# Architecture

## CI and version delivery

Chrome delivery is implemented as a separate reusable workflow with explicit activation, scoped OIDC permission and Google WIF service-account impersonation. It uses no stored JSON key or credentials file; the access token is short-lived and passed only to the delivery process. A manual run is read-only status; matching pushed tags may upload the exact SHA-256-verified tested ZIP and submit review after upload success, with warnings blocking and review enabled. Other pending versions, policy warnings and upload/API failures stop rather than cancel or overwrite existing work. Production account binding/variables remain incomplete until verified in the owner's console.

Ordinary push/PR/manual workflows build read-only and retain temporary artifacts. Version-tag pushes add a dependent GitHub Release job with isolated contents:write. Package/manifest/tag versions must match; the tagged commit must be merged into the default branch. The release job downloads the same run's raw ZIP without extraction, verifies its build SHA-256, creates a draft with the asset and publishes it. Existing releases are not overwritten. 0.x releases are prereleases. No persistent store/cloud credentials are committed. Chrome submission uses the separate explicitly enabled workflow described above; Cloudflare deployment remains independent. See releasing.md for operator steps; AGENTS.md defines agent maintenance boundaries.

## Store preparation and private storage

The current release candidate keeps the existing disclosed single-action website/Cloudflare consent flow. Browser-local MT is attempted where available; MyMemory and official keyed/self-hosted MT require a separate connection. Experimental Google web/Bing/Edge HTTP adapters are absent from the production provider import graph. Known saved consent is cleared and their options hidden, with worker-side tests refused. Historical protocol fixtures remain source-only. No cloud deployment or store submission is automated.

`createPrivateStorage` mediates all background local-store calls. Keys, history, vocabulary (including opted-in context) and analytics are encrypted per field using AES-256-GCM, fresh 96-bit IVs and AAD bound to vault ID/field/schema. Without a vault, ciphertext and the random 256-bit data key live only in trusted storage.session memory. The default 100-row history remains usable without a password; browser restart, reload/update/disable clears session data.

An optional password vault wraps the random data key with an AES-GCM key derived by PBKDF2-HMAC-SHA-256, a random 128-bit salt and 600,000 iterations. Only the salt, fixed derivation parameters, wrapped key and ciphertext are persisted. Neither password nor plaintext data key is on disk. Unlocked data keys remain in restricted session memory across service-worker suspension; restart or explicit Lock removes them. Remembered API keys require the unlocked vault. Private records pause while locked; content receives a redacted unlock flag for the selected remembered-key LLM, and keyless AI can operate independently. Lock/unlock/erase advance history generation; late writes are rejected. Wrong passwords/tampering preserve ciphertext. Explicit confirmed erase is available even if metadata cannot be read.

Legacy plaintext fields are moved into protected session storage before old fields are removed; legacy persistent keys become session keys and their remember flags are cleared. Update-time migration opens the vault notice so users can opt into persistent protection before session end. An interrupted migration never removes its source before replacement succeeds. If a vault is locked, legacy migration waits for unlock. Non-key settings/site preferences remain ordinary local configuration and are disclosed separately. This design protects locked persistent data, not a compromised OS or complete access to an unlocked extension. Configuration/practice exports exclude vault data; explicit history export remains plaintext by user request.

Policy Markdown is the content source for two offline HTML pages built into the extension. Shared footers expose the correct language and a vault-lock entry. Store descriptions, permission/data declarations, reviewer steps and synthetic real-UI screenshots live in `store/`; user READMEs and `DEVELOPMENT.md` separate user tasks from build/operations instructions.

Input committed during an initial or refreshed policy lookup is rescheduled only for the same connected editor and unchanged draft, after access rules arrive. IME candidates and Escape-cancelled work stay inactive. Vault deletion also clears remember-key preferences so fresh session credentials can be saved without recreating a vault.

## Website policy

`settings.siteMode` is `blacklist` by default and can be changed in Settings or the popup. Blacklist mode ignores the retained allowlist and denies matching blocklist hosts. Whitelist mode requires an explicit matching allowlist entry (empty means none) and still denies the blocklist. Host matching supports exact domains and `*.` boundaries; suffix lookalikes do not match. Migration keeps previously explicit allowlists in whitelist mode rather than broadening their scope.

Application policy does not grant Chromium permissions. `siteAccess` verifies HTTP(S), a saved exact/all-websites origin scope, and the current browser grant; `forSite` then applies the list policy. The blacklist-mode quick start requests optional HTTP(S) grants on the user's click, once. Site scripts remain registered within these granted scopes so a blocked site's manual shortcut can show a local status/removal panel; automatic handlers do not snapshot/process blocked input. White-mode Add website updates both its grant scope and allowlist entry.

`set-site-blocked` is a narrowly scoped content-writable site action. It uses the sender's actual URL, permits adding/removing only that exact hostname, checks site access even while blocked, and requires blacklist mode. Supplied hostnames/tab IDs from content scripts are ignored. Trusted popup requests identify a real browser tab, whose URL/grants are verified by the worker. Wildcard entries cannot be removed through this exact-host action; the UI routes inherited matches to Settings. Writes are serialized and preserve provider preferences/keys and both lists. `set-site-mode` is trusted-UI-only.

The tooltip includes a collapsed Website settings disclosure in results/error states, without a redundant normal-site blacklist badge. Blocking invalidates in-flight suggestions, clears unsent numeric deltas, removes old Apply/result controls, and leaves only a local status/undo panel. Manual reopen does not read or transmit the draft. Settings broadcasts are change notifications; each frame fetches its own effective defaults and safe UI-language preference. Every Apply and subsequent worker request rechecks current policy. Already-sent remote requests cannot be retracted.

## Console localization

It cannot alter consent, endpoint URLs, credentials, global activation or list policy. It stores up to 300 hosts separately in trusted local storage and rejects new-host overflow rather than silently changing an older host's routing. Reset deletes only the sender's entry. Every worker request recomputes effective site settings before selecting credentials, caps and provider lanes; deleted selected profiles disable LLM rather than routing to another provider. Content receives only its own override, global inheritance labels and a redacted list of profile choices. Cross-frame updates use versioned fetches of the frame's own settings. Saving cancels previous results and Apply, preserves the editor, and starts no request until the next input/shortcut. Primary LLM replacements wait while a site select is focused; unsaved form values/open state survive the replacement. Disconnected disclosure toggle events cannot reopen a new tooltip.

The four extension UI pages share `src/ui/i18n.js`, an English-source message catalog in `src/locales/zh-CN.js`, and a pure `resolveLanguage` helper. Static text, titles, placeholders and accessibility names are explicitly marked with data-i18n attributes. Dynamic messages use parameterized translations; dates and numbers use the resolved locale. No user/provider content is traversed or translated.

## Provider contract

Basic adapters expose `id`, `name`, `category`, `pairs`, `available(config)`, and `translate(text, config)`. Chrome's document adapter exposes availability states, prepare, and translate separately because model downloads need user activation and the API does not run in service workers. External adapters share bounded JSON fetching, timeouts, no cookies, no redirects, generic safe error messages, and plain result normalization.

`BasicRouter` uses the supported subset of saved `basicOrder` (MyMemory → configured LibreTranslate → configured official Azure → configured official Google Cloud) after eligible local translation. Retired IDs remain only for configuration compatibility and cannot be routed by the production provider registry. Complete legacy five-engine orders retain their sequence and append googleweb/bing; migration never enables them. Manual selection runs that engine first, followed by the order if `basicFallback` is enabled; with fallback disabled only the selected engine is tried. Each external candidate must have BOTH stored text consent and a current Chromium endpoint host grant. First successes include engine identity plus an input-free attempt summary. Auth/invalid-request failures block until a settings change/test. Rate/quota failures respect Retry-After/cooldown. Two consecutive other failures trigger a one-minute cooldown; input-length rejection does not damage provider health. Health is kept in storage.session across worker restarts. No blind retries within a provider and no unauthorized fallback.

The Microsoft Edge no-key adapter is an explicitly labelled experimental browser endpoint, distinct from the official Azure adapter. It POSTs a string array to /translate/translatetext with the selected direction (zh-CHS ↔ en). It never requests login cookies or scrapes bearer tokens. Its availability and third-party integration contract are not guaranteed by Microsoft. Official Azure POSTs Text objects to /translate?api-version=3.0 with zh-Hans ↔ en, the user's Ocp-Apim-Subscription-Key and optional Ocp-Apim-Subscription-Region. Keys default to trusted session storage exactly like other provider keys.

The former four-recipient quick-start control is unavailable in the store candidate. Only supported, individually connected remote MT participates in production routing. A permission grant alone does not imply text consent. `test-basic` with a supported concrete ID disables fallback; with `auto` it tests the authorized remote chain using a fixed synthetic phrase. `basicStatus` in storage.session records safe engine/status metadata without draft text and is returned only to trusted UI pages for diagnostics.

`src/providers/web-translation.js` implements independent googleweb/bing adapters. Google uses the legacy gtx GET contract, joins translated segments and maps zh-CN/en. Bing fetches `/translator` as bounded text (1,048,576 UTF-16 units), parses only the required anonymous JSON-array/IG/IID literals without executing scripts, then form-POSTs to `/ttranslatev3` using zh-Hans/en. Requests omit cookies, referrers and redirects. It never follows an ungranted regional domain; the default is cn.bing.com, with an editable base URL requiring reconnection. Worker-owned provider instances retain a coalesced per-endpoint Bing page-parameter cache (at most four entries, at most ten minutes) solely in memory. Expiry/failure invalidates the cached session; no immediate request retry or verification bypass occurs. A page verification challenge or HTTP 401/403 becomes unavailable, rather than suggesting a nonexistent user API key. Google caps input at 5,000 UTF-16 units; Bing at 1,000, without chunking. Length failure does not damage health and can fall through to another authorized provider.

The router passes web adapters a late-access check. Before posting a Bing draft after page loading, it rechecks current service consent/endpoint, browser grant and (for website requests) global enablement, site grant and list policy. Thus disabling a service during anonymous page bootstrap prevents the later text POST. Provider metadata/attempts/health contain no page parameters or draft. Configuration backups automatically include the new provider endpoints and per-site engine IDs while omitting consent and temporary parameters. The existing keyed Google Cloud and Azure adapters remain distinct.

Content starts independent `suggest` lanes (`mt` / `llm`) concurrently after debounce. The worker still validates enabled state, sender site access, list rules, consent and host permission on each lane; MT never routes into LLM, and LLM never falls through to another provider. Old no-lane messages retain single-result compatibility. Eligible on-device MT runs in the document concurrently with the worker's LLM request; authorized remote fallback remains inside the MT lane. Network requests do not run within the serialized storage-write queue.

Each editor request holds both transient results under the same source/sequence/policy guard. No loading-only tooltip appears. The first usable result opens the card; LLM is always preferred when available, and MT becomes a closed details panel regardless of arrival order. Updates to the same LLM primary modify only the secondary area, preserving vocabulary interaction. Pointer-down queues a primary replacement until after the click, and Apply cancels queued/late results before asynchronous editor operations. Suggestion metrics count once per source request; acceptance/AI characters count only an explicit successful Apply. Individual lane failures preserve the other lane; all-failed requests expose bounded safe errors. No draft/result cache or progress text is persisted.

`targetLanguage` has a global `en` / `zh` default (`en` initially), with optional exact-host overrides, independent of console locale. Popup changes are trusted-worker mutations and broadcast invalidation. Target-aware routing polishes already-target-language text via LLM, translates opposite/mixed text, and reserves Explain for LLM. MT adapters use the derived pair in both availability checks and translation bodies; local translators cache each direction separately. The LLM prompt names the target language; Chinese output does not propose English vocabulary highlights.

LLM configurations include `thinking: false` and `thinkingProtocol: auto` by default, including migration of old profiles. The adapter maps MiMo/DeepSeek to `thinking.type`, SiliconFlow to `enable_thinking`, Ollama Chat Completions to `reasoning_effort`, eligible OpenAI models to `reasoning_effort`, and Gemini 2.5 Flash to `thinkingConfig.thinkingBudget`. Unknown compatible servers can explicitly choose a protocol (including template kwargs) instead of receiving unsupported private fields. Known reasoning-only models reject thinking-off locally with a useful configuration error. Reasoning content is never rendered; Gemini thought parts are filtered. Sampling temperature is omitted for enabled thinking in compatible requests. A failed attempt still consumes its profile's local request cap; this is not a token-cost budget.

## Messages and trust

Trusted UI messages must originate from this extension's URL. Browser tabs containing extension options/dashboard pages are trusted; ordinary content scripts are not. Content scripts can request a redacted configuration, submit an ephemeral draft for processing, submit numeric metrics, save explicitly selected vocabulary, manage validated defaults/blacklist/placement for their own granted hostname, and open Settings. They cannot retrieve full state/credentials, test arbitrary endpoints, save global settings, forget keys, reset/export practice data, or modify site grants. The worker derives hostname from sender.url and ignores supplied analytics text fields. Permission revocation is rechecked on every request. Revocation cannot retract text already sent. Apply is blocked while an asynchronous frame-policy refresh is pending; a changed policy invalidates prior results before they can be applied.

The UI requests exact-origin host permission on a user gesture, then saves explicit provider consent. Endpoint field/provider changes clear UI consent and moving an endpoint drops its previous stored key. Host permissions are not treated as application consent: a site grant on a local server does not authorize that server as a provider. Removing a site from application settings immediately stops content processing even if Chromium still retains that host grant. Provider Revoke removes application text consent; the Chromium grant may remain for shared origins and can be removed in browser extension settings.

All local and session storage is restricted to TRUSTED_CONTEXTS at worker startup. Content receives its own preferences and redacted LLM choice labels, without endpoints, keys or vault material. Keys default to session memory; persistent keys require the password vault described above. Practice-data exports use analytics/vocabulary whitelists, excluding sentence contexts. Configuration backups use a separate allowlisted schema. There is no sync storage, telemetry, analytics server, or remote code.

## Provider connection controls

The settings page exposes one **Connect and test** action for each LLM/basic provider, replacing separate authorization and test buttons. Adjacent disclosures explain that connection permits input-text processing. The click validates the form and endpoint, directly requests the exact browser origin within the gesture, saves consent (and enables the selected LLM), then sends the existing synthetic test. Existing browser grants are reused by Chromium. There is no grant or consent on ordinary Save, profile selection, import, or fallback. A denied grant causes no save/test. A changed profile/provider/endpoint while the permission request is pending cancels the action. Worker consent and origin checks remain independent and mandatory.

Connection does not activate another LLM profile. A successful save followed by a failed test leaves the service enabled, with the actual test error shown; enabled means permission to process text, not a successful connection-health claim. **Disable service** appears only for a consented service and saves consent=false, retaining keys, configuration and native browser grants. Already-sent requests cannot be recalled. The fallback-chain test still only tests previously enabled providers and requests no new grants.

## Editor and suggestion lifecycle

Capture focus/beforeinput/input/composition events at the document boundary. Ignore sensitive fields and untrusted programmatic input for analytics and automatic scheduling. A source snapshot is held in a WeakMap for the current editor and never persisted. A debounce adds 600 ms for unfinished sentences. Composition commits once at compositionend; intermediate updates cannot trigger requests.

Each edit, blur, mode change, pause, or exclusion invalidates a monotonically increasing request ID. Before displaying or applying a result, verify request ID, exact source, current editor, connection, composition status, and current policy. Late remote replies can finish but cannot resurrect stale suggestions. Automatic provider errors are shown once per message per minute to remain unobtrusive; manual requests always show errors.

Native setters plus bubbling input events update ordinary controlled inputs/textarea. Plain contenteditable, plain ProseMirror paragraphs and unformatted Draft.js wrappers use browser insertText. Structured editors never fall back to textContent replacement. Plain Slate permits only known text/paragraph wrappers and layout-only styles; reading excludes placeholders and zero-width markers. Settled beforeinput processing also detects model updates when Slate prevents native input; unchanged snapshots deduplicate corresponding input events. Apply lets Slate synchronize the whole-editor DOM selection before dispatching a plain-text paste. If an override ignores paste without changing the draft/selection, native insertText may feed input reconciliation. Both paths recheck source, selection and current website/IME/request policy; formatted marks, voids, nested editors and unsupported frameworks retain Copy. Pointer activation preserves focus; keyboard activation remains available. Apply checks the value again after the next animation frame and only records acceptance if the replacement remains in place. A host can still asynchronously rewrite input later. Suggestions and vocabulary are rendered using textContent/text nodes, never untrusted HTML.

## Data schema

- `settings`: version-0.1 preferences, per-provider endpoint/consent, key-storage choice, website origin grants and host rules. Keys live in separate `keys` entries.
- `sitePreferences[hostname]`: up to 300 exact-host routing overrides (`mode`, `targetLanguage`, `basicEngine`, `llmProfileId`). Absent fields inherit global defaults; null profile means MT only. Separate from global settings so stale console forms cannot overwrite them. No drafts, keys, URLs or endpoints. Practice-data reset preserves these preferences.
- `analytics[YYYY-MM-DD]`: numeric typed/chinese/english/pasted/ai/suggestions/accepted totals and the same counters under `sites[hostname]`; at most 366 days. Dates follow the browser's local calendar.
- `vocabulary[]`: bounded word/meaning/explanation/pronunciation/example/status/date; optional context only with explicit save-time consent; 2,000-item maximum. Known words are filtered on-device and not sent to the provider.
- `usage`: local date and attempted LLM request count. Reset explicitly clears this counter.
- `health` / `llmHealth`: session-only failures, blocked flags and next eligible time.
- `basicStatus`: session-only last engine, timestamp, safe failure message and per-engine status codes. No source text or credentials. Settings holds `basicFallback` and an ordered allowlisted provider-ID list.
- `tooltipSizes[hostname]`: up to 200 local small/medium/large choices, independent of website routing, positions and practice data. Export/import includes this map; older files default to an empty map and Small.

Counts represent inserted independent characters and estimated new English word starts. They are not final document length; deletions do not subtract practice. Paste/drop, automatic replacements, undo/redo, and AI Apply are separate/excluded from independent counts. External AI text manually pasted is paste, not detectable as AI. Pending numeric deltas flush after a short pause and on pagehide; abrupt tab/process termination can lose the last small batch.

## Tests

`core/llm-providers.js` centralizes validated LLM provider IDs, display names, base URL presets and model/console hints. Settings remains a configuration client, with all HTTP requests in provider adapters. MiMo sends `api-key`, `max_completion_tokens`, and `thinking: {type: 'disabled'}` to `/chat/completions`; SiliconFlow sends Bearer authentication and `max_tokens` to the same relative path. Both parse only `choices[0].message.content` as bounded suggestion JSON, ignoring reasoning text. API base URLs and model IDs remain editable; presets do not grant consent or host access.

`llmProfiles` holds up to 20 named configurations with validated unique IDs and independent endpoint/model/consent/storage choices. `activeLlmId` chooses exactly one; `llm` is its compatibility projection so prior single-configuration clients and installations migrate to ID `default`. That projection is the global default; an exact-host override may select another existing profile without changing global activation. Settings separates editing selection from activation, preserves draft key fields per profile in page memory, and lets Test Connection target an inactive saved profile without activating it. Trusted popup activation changes only the selected ID/projection. Keys remain separate in trusted storage: legacy/default `keys.llm` and other `keys['llm:'+id]`, never in profiles or redacted content settings. State includes presence booleans only. Save preserves a key only for its existing profile ID/provider/endpoint, moves it between session/local according to its own preference, and removes deleted profiles' keys. Forget all keys clears every profile. Request counts and session health are scoped per profile; numeric total usage remains available. No automatic LLM-provider fallback occurs.

Tooltip website controls are an initially collapsed, single-line Website settings disclosure. Its two-column form offers default action, target language, saved LLM configuration (including MT only) and basic translation engine, each inheriting global settings unless overridden. Save and Reset are explicit; no redundant allowed/blocked badge appears in the summary. Blocking automatically opens the status panel so the undo action remains visible. Expansion is an ordinary keyboard-accessible disclosure and does not read or send draft text.

Tooltip placement is independent of settings/analytics. The header handle supports pointer capture (mouse/touch/pen), arrow-key movement (Shift: larger steps) and a compact reset control. Coordinates are normalized within the available visual viewport travel, so resize, zoom/viewport changes and content growth keep the panel visible without overwriting the preferred placement. A ResizeObserver repositions expanded vocabulary/details; scrolling follows the editor only before a manual position is chosen. Result replacement and dismissal preserve placement; cancelling a drag restores the previous placement. Pointer gestures defer primary-result replacement until release, preserving Apply and drag targets.

The header also has a localized Small/Medium/Large select beside the drag handle. Target widths are 300/380/480px, with coordinated font, padding and bounded body-height changes; Small is the default. Size changes modify attributes/layout in place, retaining Apply/results, vocabulary, unsaved site form controls and normalized preferred placement. Focus in the size select defers primary result replacement just like a site select. A narrow sender-scoped `set-tooltip-size` action validates the enum, checks current site grants and saves only the sender's hostname, evicting the oldest of 200 entries. Public settings return only that hostname's effective size. A size-only broadcast applies layout without invalidating current requests or results; no new inference is triggered. Normalized geometry clamps all sizes to the current visual viewport, with host scrolling for content taller than the window.

`tooltipPositions[hostname]` stores only `{x,y}` in trusted local storage, up to 200 recently moved hosts. Runtime get/set/reset derives the exact hostname from the browser sender and rechecks saved website access plus browser permission; callers cannot specify another host. Blacklisted-site status panels may still be moved. No paths, drafts, credentials, timestamps or events are stored. Placement writes do not broadcast settings or cancel in-flight translation. Reset removes only the current hostname; practice-data reset preserves this UI preference. Preferences are local to this browser profile and shared across paths/protocols/ports for the same hostname; different subdomains have separate positions.
